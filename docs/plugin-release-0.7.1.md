# 0.7.1：让累计备份和增量进度直观可见

日期：2026-10-27。基于用户实际试用反馈修订 0.7.0 的数量展示。

## 问题与核对

旧任务页突出“本次已保存”，每次新任务从 0 开始，容易误以为没有识别历史备份。代码已取得的抖音列表总数没有渲染，首页三个来源入口也没有显示各自的累计数量。

本次对用户指定外接盘备份库进行了只读核对：v1 完成索引的全部作品 ID 都已进入 v2，未发现旧完成 ID 丢失。v2 任务正在保存新增作品并跳过已有作品。源库没有被离线改写，没有扫描或删除真实媒体。

## 数量展示

- 首页仍以全库唯一已备份作品数为汇总；喜欢/收藏入口同时显示平台列表总数和该来源的本地累计备份。选定文件夹后自动只读获取账号总数，不必先点击下载。
- 任务主区并列“喜欢/收藏总数”和“累计已备份”，启动、暂停、续传和新建下一轮任务时都接续目录中的累计记录。
- “本轮新下载 +N”单独展示，只计算本轮实际完成保存的作品；“已检查、已有跳过、待处理、需处理”展示本轮进度。
- 文案明确从最新作品检查、已有备份自动跳过，不修改现有分页终点或用不可靠的提前退出替代完整检查。
- 喜欢和收藏的本地累计包含历史来源关系。用户取消喜欢或收藏后，文件仍保留，所以累计可以大于当前平台总数。两者不相减作为待下载数量，不拿累计数除平台总数计算覆盖率。
- 平台未提供总数字段时显示“暂不可用 / —”，不是 0；显式提供 0 时才展示 0。恢复任务可先显示已记录的总数，并注明是上次读取。
- 关注任务显示所选作者人数和该文件夹所有关注来源的累计作品，避免把关注人数当作作品总数。

## 验证

`npm run check` 包含数量模型与真实 Sources 解析回归：历史累计 8,767 与平台 8,383 分别保留、未知与零的区别、账号不匹配时不串用总数、旧记录回显。

`npm run check:ui` 使用独立 Chrome、合成接口和真实 OPFS。初始目录有 5 个历史喜欢作品，本轮 24 个可读取作品中 3 个已有、21 个新下载，最终喜欢累计为 26。再次增量任务保持累计 26、显示本轮 +0、跳过 24，且不再请求已有媒体。另覆盖平台收藏总数缺失、暂停刷新续传、来源复用、作者分页、重复整理和窄屏。

数量与增量展示由目录记录和只读平台响应驱动；真实账号全量下载仍由用户试用确认。
