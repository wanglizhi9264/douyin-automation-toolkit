# 抖音备份插件产品 Spec v0.1（讨论稿）

> 已由 `plugin-product-spec-v0.2.md` 取代。用户在后续讨论中取消扫描确认页，改为点击即下载、分页与下载流水线并行、闲时整理重复文件。本文仅保留讨论历史，不能作为当前实现依据。

日期：2026-10-27。审查基线：插件 0.6.2，提交 3533ac2。

本文描述建议的目标产品，不表示现有实现已满足。此轮只整理产品定义，不修改插件运行代码，也不迁移历史媒体。

## 1. 已确认的产品决策

用户已确认：

1. 同一作品在同一个备份库只保存一份媒体，保留喜欢、收藏、关注作者等多个来源关系。
2. 先完整扫描所选列表，核对本地库，展示待下载清单，用户确认后再下载。

其他建议均为待讨论项，不能视为已获准实施。

## 2. 产品定位与边界

定位：把用户选择的抖音作品备份到一个可继续使用的本地资料库，让用户明确知道选了什么、已有多少、还需下载多少、哪些没有完成。

核心流程：确认账号与备份库 → 选择内容 → 扫描与核对 → 确认清单 → 下载 → 查看结果。

建议主界面只承担备份。喜欢转收藏、私信分享点赞归入独立的“更多工具”，不自动串入备份。保留喜欢、收藏、指定关注作者三个内容来源；关注作者必须明确选择作者，不默认全选。

产品内使用“作品”作为计数单位。一条图文、多段视频作品均算一条作品；图片数、视频段数、文件数只在作品详情显示。

## 4. 三套数量，三个明确的位置

| 数量 | 定义 | 展示位置 | 能否直接用作任务分母 |
| --- | --- | --- | --- |
| 抖音显示数量 | 平台资料或列表接口公布的计数，附获取时间 | 内容选择区的次要信息 | 不能 |
| 本地已备份 | 当前备份库记录的唯一完整作品数，附状态/核对时间 | 备份库摘要 | 不能 |
| 本次待下载 | 本轮完整扫描的去重作品，核对本地后仍需下载的集合 | 确认清单与当前任务 | 可以，确认后固定 |

禁止使用“平台数量－本地累计数量”计算待下载。不同来源的数量不能相加作为全库唯一作品数。数量未取得显示“尚未读取”，扫描不完整显示“未完成核对”，读取出错显示“读取失败”；只有确认集合为空时才能显示 0。

本地首屏可快速读取上次成功记录，但必须标明“库记录 · 最近核对时间”；未经文件核对，不宣称实时完整性。显式提供“核对本地库”。

### 4.1 本轮集合与数量守恒

- F：在本次所选来源中实际识别到的唯一作品 ID 集合。跨来源去重，但保留每条来源关系。
- B：F 中已经有完整本地副本的作品。
- D：F 中当前判断可以尝试下载，且缺少完整本地副本的作品，包括需要补齐媒体段的作品。
- U：F 中缺少完整副本，且当前不可访问或信息不足以判断能否下载的作品。
- X：F 中不支持的媒体类型等明确排除项。
- B、D、U、X 互斥，满足 F = B ∪ D ∪ U ∪ X。

确认页展示：扫描识别 |F| 条；已有备份 |B| 条；本次待下载 |D| 条；暂不可备份 |U| 条；不支持 |X| 条。后三项为零时可收起零值细节。

“完整扫描”表示所选列表分页达到可信结束，不表示平台在扫描期间提供了不可变快照。显示扫描起止时间与每个来源的完整性；平台计数与实际识别数不一致时显示差异，不能把差值称作“已删除”或“下载失败”。未列出的作品没有 ID，不能虚构为 U 中的具体作品。

### 4.2 示例

假设平台显示喜欢 1,000 条，本轮实际识别 970 条。其中本地已有 850 条，可下载 115 条，暂不可访问 5 条。

确认页：已识别 970；已有 850；待下载 115；暂不可备份 5。另提示“平台显示 1,000，本轮读取 970，存在数量差异”。

用户确认的下载计划为 115 条，进度从 0 / 115 开始。115 条全部成功后，显示“本次下载完成，仍有 5 条暂不可备份；平台数量差异未消除”，不能显示“1,000 条全部备份完成”。

## 5. 备份库与去重

备份库由当前账号、目录身份、作品记录、媒体和任务记录组成。同一个库内以稳定作品 ID 去重，来源是多对多关系；两个不同作品 ID 即使内容相似也不自动合并。

已在喜欢中备份的作品，后来加入收藏，再扫描时只补来源关系，不重新下载媒体。全库数量仍加一次；来源视图可以同时出现，必须提示各来源存在重叠。

一条作品“备份完整”要求所有必需媒体段完整写入且必要作品记录已保存。缺图、缺段、续传文件或保存失败均不能计为完整。可选封面失败单独报告警告，不把完整视频计为媒体失败。

旧版本已经存在多个来源副本时，先识别并复用有效文件，在逻辑上合并为一个作品。升级不得自动删除、移动、覆盖旧媒体；是否整理冗余副本是后续独立功能。部分完成媒体允许补齐，不重下已完成段。

来源关系须区分“最近扫描仍存在”与“历史曾属于”，附核对时间。列表中消失只改变来源状态，保留本地媒体，不推断删除原因。

## 6. 前端结构与逐步交互

### 6.1 初次打开：建立上下文

顶部：产品名“抖音备份”、当前账号、连接状态。未登录时主操作为“前往登录”，不展示虚假的零值。

未选库时：简短说明保存到自己的文件夹，唯一主按钮“选择备份文件夹”。用户取消选择，保持原状。

选择目录后：

- 已有库：展示账号、库名称、已记录的唯一作品数、上次任务，确认兼容后使用。
- 新空目录：展示“在此创建备份库”，确认后初始化。
- 有文件但无法识别：显示“无法识别为备份库”，提供换目录/检查，不能当成空库覆盖。
- 权限不足：提供“重新授权”，不能显示本地 0 条。
- 属于其他账号：明确阻止使用并提供切换账号或目录。
- 旧库归属不明：进入身份核对，不能默认绑定当前账号。

库就绪后，目录显示为一行上下文：“备份库名称 · 库记录 850 条”，旁边次级“更换”。不把下载控制放在目录区。

### 6.2 选择备份内容

用复选项选择喜欢、收藏、指定关注作者，可多选；点击来源只改变选择，不启动下载。

平台数量作为次级文字标为“抖音显示 × 条”，不在此显示待下载量。关注作者显示“已选 × 位”，作品数扫描后得出。

选择关注作者时，就地展开作者选择，支持搜索、多选；未选作者时无法扫描。作者人数与作品数不使用同一个数值字段。

唯一主操作：“扫描所选内容”。基础设置置于次级入口，默认完整备份支持的媒体、尽可能获取最高画质；去重和复用目录是固定行为，不让用户理解内部开关。

### 6.3 扫描与核对

扫描阶段读取所选平台列表并核对本地，不下载媒体、不点赞、不收藏。允许保留扫描记录和任务元数据。

主文案：“正在扫描喜欢 · 已识别 426 条”，多来源同时显示各来源状态。总数尚未确认时不显示整体百分比、剩余条数或预计结束时间；平台数量只作为参考。

扫描与核对合为一个用户步骤，必要时文案切换为“正在核对已有备份”。对本轮候选本地副本检查必需文件是否存在、是否具有完整记录；完整内容校验另设核对功能，不承诺消除全部潜在损坏。

暂停扫描后标记“扫描未完成”；恢复时保留已有结果并去重，游标失效时明确提示重新扫描。接口失败、游标异常、限流、仅完成一个批次都不能进入“准确清单已就绪”。

### 6.4 确认下载计划

扫描完整后，显示固定摘要与可查看的作品清单：

```text
扫描完成                       喜欢、收藏
识别作品                         970 条
已有备份                         850 条
本次待下载                       115 条
暂不可备份                         5 条  查看

保存到：我的抖音备份
[开始下载 115 条]          修改范围
```

多选来源时摘要按唯一作品计数，来源详情显示各自识别数量与重叠说明。清单默认查看待下载，支持切到已有/异常；作者、描述、类型在前，技术 ID 和路径放详情。

确认计划保存账号、库身份、所选来源/作者、扫描时间、作品 ID 和分类。修改账号、库、范围或影响计划的设置会使计划失效，需要重新核对；不能拿旧分母执行新任务。

D=0 且无 U/X 时显示“本轮识别作品均已有备份”，不保留空下载按钮。D=0 但有 U/X 时显示具体例外和可执行的重试入口，不能称全部已备份。

### 6.5 下载中

确认后只执行该计划 D，不在任务中悄悄加入新作品。新出现的作品在下次扫描中处理。媒体地址过期可刷新地址，不改变作品清单和分母。

主界面切换到当前任务，来源选择区与创建入口收起；持续显示账号、备份库、计划时间和摘要。

```text
正在下载                         90 / 115 条成功
失败 2 条 · 待处理 23 条

当前作品：作者 · 作品描述
视频第 2 / 3 段 · 当前文件进度

[暂停]                         查看明细
```

成功数从本次计划的 0 开始，历史已有 B 不混入。图文全部必需图片成功后，作品成功数才加 1。处理完但失败的条目不能让“成功”进度到 100%。

### 6.6 暂停、恢复与结果

暂停先显示“正在暂停并保存”，写入可恢复检查点后才显示“已暂停”；保存失败明确提示并允许重试。恢复同一个计划，已成功项不重复计数；必要时复核尚未处理的文件与地址。

有未完成任务时，首页用一条任务提示展示来源、成功/失败/待处理和“继续任务”；“新建备份”作为次级动作。切换任务/目录需先安全暂停。关闭面板与暂停必须在产品上区分：建议提示“任务仅在当前抖音页保持运行时继续”，当前页离开或重载后通过记录恢复，不承诺后台持续运行。

任务结束区分：

| 状态 | 条件 | 主操作 |
| --- | --- | --- |
| 本次备份完成 | 所选来源完整扫描，计划全部成功，必要状态已保存，且无 U/X 等覆盖例外 | 查看本地库 |
| 本次处理结束，部分未备份 | 下载失败、U/X、已知读取差异等例外仍存在 | 重试失败项或查看未备份原因 |
| 已暂停 | 用户暂停且进度已保存 | 继续任务 |
| 需要处理 | 账号、目录权限、网络、限流或状态保存阻塞 | 显示对应修复动作 |

所有完成措辞限定“本轮实际识别的所选作品”，不承诺不可枚举的平台全部历史。最终页面展示本次新增成功、复用已有、失败、暂不可备份、明确排除与扫描差异；失败按作品计数，重试次数不重复累计作品失败数。

## 7. 信息层级与视觉原则

建议两个顶层入口：“备份”“本地库”；设置/更多工具为次级菜单。本地库入口的打开方式、是否单独标签页待确认，不能为此扩张主侧栏。

每个状态只保留一个主操作；继续任务与创建新任务不同时突出。没有任务时不展示空任务面板。不把三种来源做成三个立即执行的下载按钮。

使用白色、浅中性灰、深色文字和少量系统蓝。目录和账号用紧凑行，数量用标签和对齐区分，避免大号统计卡片、重复状态标签和多层容器。

主界面只回答：保存到哪里、这次选什么、会下载多少、正在做什么、哪些没有完成。日志、接口游标、性能、画质参数进入详情。异常原因与修复动作留在主界面。

## 8. 产品验收场景

1. 平台 1,000、本地历史 1,200 时，扫描前待下载为“未核对”，不能显示 0 或负数。
2. 喜欢 100、收藏 80、重叠 30：所选唯一作品 150；不显示目标 180。
3. 同一作品已由喜欢备份，再从收藏扫描命中：媒体不重下，补充收藏来源；本地唯一总数不增加。
4. 本地累计 900、本轮识别 850，二者交集 800：已有 800，缺少 50；不能算成待下载 0。
5. 本地其他来源中已有完整作品：计入本轮已有，不要求为当前来源再复制。
6. 未识别全量、分页失败、批次达到 100 但仍有下一页：停在扫描未完成，不给出准确最终计划。
7. 清单确认 115 条、历史已有 850：任务从 0/115 开始；90 成功、2 失败、23 待处理时数量守恒。
8. 图文十张缺一张、多段视频缺一段、续传未结束：不计完整；恢复只补缺少部分。
9. 计划所有作品处理过但有失败：不能报成功 100%，保留重试和失败原因。
10. 扫描、下载中切换账号、换库或撤销权限：正确阻止、保存原任务，不混用库数量。
11. 缓存/目录读取失败与文件缺失：显示问题，不能用 0 或历史 max 掩盖；修复缺失文件进入清单。
12. 历史作品不在本轮列表：保留媒体，来源状态附核对时间，不称为已删除作品。
13. 确认后远端新增作品：本轮分母不变，下次扫描发现新增。
14. 旧版多份副本：逻辑去重后数量一致，旧媒体无自动删除或移动。
15. 下载成功但关键记录保存失败：显示待恢复问题，不能提前宣告任务安全完成。

## 9. 尚待讨论

1. 是否采纳“备份为主，喜欢转收藏/私信处理收进更多工具”的功能层级。
2. 本期主流程是否同时支持三个来源多选；建议支持，统一扫描与去重后只生成一个计划。
3. 本地库浏览方式：建议侧栏只展示摘要与入口，大清单在独立页面查看。
4. 版本范围：建议先完成数量语义、目录规则、扫描确认、去重与任务结果，再调整视觉；旧媒体清理和自动周期同步不纳入本期。

以上确认后再形成 v1.0 定稿与实现拆分。不得把本讨论稿当作已实现功能发布说明。
