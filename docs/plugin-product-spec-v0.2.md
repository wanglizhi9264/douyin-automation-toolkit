# 抖音备份插件产品与任务 Spec v0.2（讨论稿）

> 2026-10-27 试用修订：主界面补充喜欢/收藏平台总数与本地累计已备份，本轮新增下载独立展示。历史来源累计可大于当前总数，禁止据此计算待下载差值。具体实现口径见 [0.7.1 修订](plugin-release-0.7.1.md)。

更新：2026-10-27。代码审查基线：插件 0.6.2，提交 3533ac2。

本文取代 v0.1。只定义产品与技术边界，尚未修改插件实现，也未执行媒体整理、删除或账号操作。

## 1. 本轮已明确的方向

1. 首页以选择文件夹、下载喜欢、下载收藏、下载关注列表四个主要操作为核心。
2. 选中文件夹后，首页展示这个备份库已下载的数据量。
3. 点击喜欢或收藏，进入任务页并立即执行；取消完整预扫描、计划确认及再次确认下载。
4. 点击关注列表，进入作者选择页，选择作者后直接下载。
5. 任务优先下载；列表发现、轻量检查、下载和状态保存分开调度。
6. 完整本地核对、重复文件整理放在用户主动触发的闲时操作。
7. 不以 100 条作为任务总上限；页面批量、队列容量与任务结束条件明确区分。

下述并发数、信息标签与维护实现为本稿建议，需经实现和实测验证，不是当前能力或性能承诺。

## 2. 产品定义

产品帮助用户把喜欢、收藏以及所选关注作者的作品持续下载到本地文件夹。默认点击即执行，已有记录自动复用，失败和暂停可恢复。

主页负责展示库与入口；任务页负责展示当前工作与结果；维护功能负责整理历史数据。普通下载不会自动点赞、收藏、处理私信或删除历史媒体。

一条作品是计数单位。一条图文的十张图片仍是一条作品；一条多段作品须所有必需媒体段完整，才算一条成功。

## 3. 首页

### 3.1 未选择目录

显示产品名、当前账号、简短说明和主按钮“选择文件夹”。下面的三个下载按钮可见但不可用，说明“先选择保存位置”。不显示伪造的零条作品。

### 3.2 目录就绪

建议布局：

```text
抖音备份                         当前账号

保存位置：我的抖音备份            [更换文件夹]

已备份 11,352 条作品
已完成媒体约 128.4 GB · 记录更新于 14:32

[下载喜欢]
[下载收藏]
[下载关注列表]
```

四个主要操作固定，不增加“扫描”“确认计划”“一键完整备份”按钮。整理备份、库详情与设置放在次级菜单，避免主页面重新堆叠。

首页不显示平台喜欢总数、不显示未核对的待下载量，也不并列放三张来源统计大卡片。

### 3.3 首页数据口径

| 字段 | 定义与展示约束 |
| --- | --- |
| 已备份作品 | 当前库成功记录的作品 ID 并集。相同作品在喜欢、收藏和关注中只计一条 |
| 已完成媒体大小 | 库记录中所有已完成物理媒体文件的累计大小，按物理文件去重，同一文件只加一次；不同路径的重复副本仍占空间，须计入 |
| 记录更新时间 | 最近成功提交库状态的时间；不等同于最近逐文件检查时间 |
| 最近核对时间 | 放库详情，说明何时检查过实际文件与记录 |

“11,352 条”是基于库记录，不宣称每次开面板都实时逐文件验证。大小标“约”，不冒充包含所有临时文件、杂项与外部改动的操作系统目录占用。旧库缺大小记录时显示“媒体大小待统计”，不为补一个数字阻塞下载。

库详情可展示来源关联数量，并说明各来源可能重叠；不能把来源数量相加当作全库作品数。

已有作品新增来源或新增重复副本，不增加唯一作品数；新增物理副本会增加媒体大小。首次成功补齐一条作品才使唯一作品数加一。

## 4. 文件夹选择规则

- 新空目录：选择动作即表示使用它，直接创建库，不加常规确认弹窗。
- 可识别历史库：快速读取库摘要与紧凑索引，直接使用，不先遍历所有媒体。
- 已有文件但历史记录缺失或损坏：展示“需要核对历史库”，提供核对与换目录；不能伪装成空库覆盖。
- 权限失效：展示“重新授权”；用户取消时保持原目录。
- 账号不符：明确提示换账号或换目录，阻止向不匹配的库写入。
- 旧库归属不明：保留现有数据，要求先核对身份，不默认绑定当前账号。
- 原生目录授权由浏览器处理，产品不重复叠加常规确认。

重新选择文件夹只切换当前库视图，不清空其他库的历史数据。下载中的任务不可直接换库，须先暂停并保存。

## 5. 三个下载入口

### 5.1 下载喜欢、下载收藏

点击后直接进入对应任务页：快速校验账号/目录 → 读取第一页 → 发现可下载作品即开始传输，同时准备后续页面。

不等待整个列表扫描完毕，不先生成待确认清单，不读取全库大快照，不生成全量 HTML，不执行全盘查重。

任务仍需遍历所选列表，才能发现未下载作品，但检查与下载交叠推进。遇到一页全部已下载不能擅自推断后续没有缺失，除非另有可验证的增量边界协议；本期默认一轮分页，不为留存统计再额外扫描一轮。

### 5.2 下载关注列表

进入独立作者选择页，提供搜索、多选、已选人数以及“下载所选作者”按钮。记住上次选择，必须让用户看见当前选择；不默认选择全部关注账号。

点击“下载所选作者”后直接执行，不再确认。逐作者、逐页发现作品并交给统一下载队列，不等所有作者全部同步完成才下载。

作者列表本身支持正常分页，不只展示首批作者；所选作者作品也必须持续分页。作者数与作品数分开：例如“作者 2 / 8 · 张三；本次已保存 238 条作品”。

单作者读取失败记录其状态，在无账号/限流等全局阻塞时继续其他作者，结果标部分完成。全部所选作者达到可信分页终点且队列处理结束，才算本次范围处理完。

### 5.3 继续与互斥

同一库同一时间只有一个下载任务。任务运行时，点击对应来源按钮打开现有任务；其他来源显示暂不可启动，避免出现多个不可见的并行任务。

已暂停时，原来源按钮保留“下载喜欢”等主名称，次级提示“有暂停任务，点击继续”；点击直接恢复，不增设首页主按钮。暂停任务默认恢复原作者范围；新建不同范围须结束或保留归档原任务，不能悄悄覆盖其进度。

## 6. 任务页：平台、本次、本地各有位置

建议布局：

```text
‹ 返回                         下载喜欢
保存到：我的抖音备份

本次已保存 238 条
已存在 76 条 · 失败 2 条
已发现待处理 14 条（下载中 2 条）

正在下载：作者 · 作品描述
传输 8.2 MB/s · 当前文件 46%

列表：已读取 330 条，仍在读取
抖音显示喜欢 12,345 条 · 仅供参考

[暂停]
```

### 6.1 数量定义

以当前任务内去重的作品 ID 计数，不把分页重复返回算成两条。以下状态互斥：

- C：本任务已读取的唯一作品。
- S：本任务新完成的作品，含恢复后补齐的作品；不含之前已完整存在的作品。
- E：已有可复用完成记录，因此无需本轮再下载的作品。
- F：重试耗尽后仍失败的作品。
- X：已明确不支持的作品。
- P：已发现但仍待处理的作品，包括准备详情、排队、正在下载与待重试。

始终满足 C = S + E + F + X + P。界面主要展示 S、E、F、P；X 非零时展示原因。失败以作品当前最终状态计数，重复尝试不累加失败作品数。

扫描/列表发现尚未结束时，P 只是“已发现待处理”，不是整个喜欢列表还剩多少。不得以平台总数减本地历史量计算待下载。

### 6.2 进度显示

- 列表未读完：不展示整体百分比；显示已读取量和是否仍在继续读取。
- 单个文件：有可靠字节长度时可以显示传输百分比；图文可显示第几张、多段可显示第几段。
- 列表读完：显示“列表读取完成”，继续清空队列；不把“读取完成”当成“下载完成”。
- 主数字始终为“本次已保存”，历史总量留在首页。下载中可持续更新首页库摘要，但不替换任务数字。
- 平台计数位于次要说明，只作参考。读取失败显示“暂未取得”，不能当作 0。
- 速度为媒体响应体的实际接收速率，包含并发连接，采用明确采样窗口；本地已写入量与网络接收量不混成同一个指标。

### 6.3 完成、失败与恢复

只有列表发现达到可信终点、P=0、无在途媒体、必要状态提交成功，任务才进入结果页。

- 无 F/X、无来源读取异常：显示“本次下载完成”，范围限定本轮实际读取作品。
- 有失败、不支持或作者读取异常：显示“本次处理结束，部分未完成”，保留重试入口。
- 分页异常/限流：显示相应阻塞原因，保留检查点，不称全部完成。
- 暂停：先“正在暂停并保存”，停止取新任务、通知在途请求、保存可恢复进度；安全停止后显示“已暂停”。保存失败单独报错。
- 重试只处理失败/阻塞目标，成功记录不能重复计数；最终结果更新原任务状态。
- 返回首页或收起面板不主动停止任务，任务引擎保持存活；刷新/关闭承载页面或重载扩展后按持久化记录恢复，不承诺浏览器关闭后仍能下载。

## 7. 技术设计：下载与准备交叠，不设全量前置关卡

```text
列表读取器 → ID 记录检查 → 有界待下载队列 → 媒体下载槽位
      ↑             队列水位反馈                ↓
      └────────── 暂停/重试调度 ──────── 完成事件
                                               ↓
                                      单一元数据提交器 → UI

闲时维护：本地核对、内容哈希、重复副本整理、报告重建
```

### 7.1 职责与并发建议

| 职责 | 工作 | 初始调度建议 |
| --- | --- | --- |
| 列表读取器 | 读取喜欢/收藏或所选作者分页，规范化必要字段 | 每任务一个生产者，受统一 API 请求节流控制 |
| 轻量检查 | ID 索引查询、任务内防重、在途写锁、记录来源 | 对本页处理，不全库遍历；按需使用 Set/Map 或数据库主键 |
| 媒体下载器 | 获取必要详情、选择候选、传输与流式写文件 | 初始 2 路媒体传输，异常降到 1 路；更高并发经实测再定 |
| 元数据提交器 | 完成记录、索引与累计字节更新、恢复日志 | 单一写入所有者，媒体可分别写入不同文件 |
| 维护执行器 | 本地核对、哈希、重复文件整理、重建报告 | 用户主动触发，单库与下载互斥；CPU 密集部分可放 Web Worker |

“两路”是整个任务的媒体连接预算，不是每条作品两路再乘图片/分段数。不得并发写同一路径；详情请求也必须纳入平台 API 请求预算，不能靠并行隐藏倍增。

队列建议高水位 64 条、低水位 16 条，作为初始可调整值。满时暂停生产，低于水位时继续预取；不把全平台作品详情或媒体 Blob 堆进内存。候选 URL 接近消费时再补取/刷新，避免预取太远导致过期。

优先复用列表已有候选，缺失或失效时才取详情。队列为空但列表仍未读完时显示“正在读取下一页”，不能报任务完成。

### 7.2 线程与进程的实际边界

浏览器扩展采用异步请求即可交叠网络 I/O，不必为每个下载创建线程。原生多进程不是普通扩展可直接调度的独立进程池；引入本地后端会改变安装方式，本期不采用。

Web Worker 适合移出哈希、批量归并、索引重建等 CPU 工作，也能处理部分异步 I/O，但不能直接访问抖音页面 DOM。带登录态的页面接口继续由现有页面桥接上下文执行，与下载器通过消息/队列解耦。

不能把 MV3 service worker 当永久运行进程或唯一进度存储。扩展任务引擎与渲染分离，返回/折叠不销毁引擎；承载页面销毁则需检查点恢复。具体承载上下文与目录句柄能力须在目标 Chrome/Edge 实测后确定，不承诺换一个 Worker 就能关闭页面继续下载。

### 7.3 必须保留在下载路径上的轻量检查

- 账号与目录权限是否可用。
- 当前作品是否已有完成记录，当前路径是否已有任务在写。
- HTTP、MIME、长度和传输是否成功；分段必需媒体是否齐全。
- 媒体和必要元数据成功保存后才记录成功；磁盘满或元数据保存失败不能只更新 UI。

ID 查表通常是近似常数时间查询，与逐文件读盘、哈希查重不是同一成本。保留它可以避免下一次点击整批重下；不要求每个命中都去读全部媒体验证。外部删改造成的索引失真由显式核对校正，出现直接证据时立即修正记录。

完整目录扫描、全文件哈希、来源消失原因核对、全量报表生成不进入逐条下载的主循环。

### 7.4 下载时与闲时的去重分工

本轮修订不再要求开跑前把所有历史副本统一成一份。

- 已有快速索引能证明同一作品已完整备份时，复用并追加来源，不为了等待闲时整理而故意再下载一份。
- 对旧版按来源保存、尚无可靠全局映射的文件，允许暂时存在跨来源副本，不逐文件查重阻塞任务。
- 本轮队列中的相同作品/相同媒体段只执行一次，使用在途锁避免两条连接下载同一路径。
- 同 ID 不同画质、不同媒体段不可直接按重复文件删除；复杂的副本归并留给维护。

索引与来源关系需支持一条作品关联多来源、多物理副本。库唯一作品数从作品集合派生，物理大小从文件记录派生，不能继续从各 scope 的累计数简单相加。

### 7.5 状态与持久化

分页检查点须在本页作品已纳入可恢复记录后推进，不能因崩溃跳过整页。队列支持恢复，已提交成功、部分写入与待重试明确区分。

完成事件写入小型日志/记录，累计摘要批量更新；写失败保留待写项并显示错误。索引、数量、进度使用一致的版本代次和可恢复提交协议，避免多个消费者各自写数字。

报告生成不阻塞每条媒体。暂停与结束先确保必要记录保存，复杂本地 HTML/全库报表可延后按需生成。不能只把必需的安全检查点也一并后移。

## 8. 100 条限制：实际情况与整改要求

当前 `shared/state.js` 的 `batchSize` 默认 100。关注分支先同步所有所选作者作品，再在 `sidebar/app.js:3740` 用 `.slice(0, batchSize)` 选下载项，因而一次只处理前 100 条。

喜欢/收藏的主要下载分支是分页循环，一页返回后逐条等待下载再读下一页，不是浏览器要求每下载 100 条强制检查。喜欢遇到已知边界后还继续完整留存核对（`:3153`）；全量状态/HTML 当前主要在暂停、结束写入（`:859`），不能误称每 100 条全量导出一次。

要求：

1. 删除关注下载的业务总量截断，直到所有所选作者分页完成、队列处理结束。
2. API 页大小只是单次请求容量，队列容量只是内存控制，状态提交批量只是保存策略，均不是用户任务上限。
3. 三种来源使用统一的生产/消费任务协议，避免关注走另一套批次完成逻辑。
4. 读取下一页与当前媒体下载交叠；网络节流仍保留，不能通过增加 Worker 绕过平台限制。
5. 没有真实耗时分解前，不把所有卡顿归因于线程或“100条检查”。

## 9. 闲时“整理备份”

产品名称建议用“整理备份”，因为这里主要清理磁盘重复副本、修正库记录；“清理内存”仅用于释放可重建运行缓存，不能混同于删除媒体或清空续传记录。

用户从次级菜单点击“整理备份”即开始，普通情况不增加确认页。下载运行中入口不可执行并提示先暂停；整理时也不能启动同库下载。

阶段：识别候选副本 → 比对并选择保留文件 → 更新来源和路径引用并验证记录已保存 → 移除已证明冗余的副本 → 重建摘要。

整理约束：

- 优先按作品 ID、媒体段标识、文件长度筛选候选，只对候选做内容哈希，不无差别重复读取全库。
- 默认只移除确认内容相同、类型/媒体段一致的副本。不同画质或内容不同的版本保留并报告；一条作品中的不同图片/视频段不是重复副本。
- 始终保留至少一份完整可用的媒体与所有来源关系；不能用不完整续传替换完整文件。
- 在所有相关路径引用和恢复记录保存成功前，不删除旧副本；支持中断恢复，重新执行不会误删保留文件。
- 普通下载不自动触发清理。旧历史文件无证据时保留，不以“未出现在本轮列表”作为删除理由。
- 整理结果展示“合并重复副本 N 份，释放 X GB；保留不同版本 Y 份”，不把移除副本数叫作品删除数。

整理后唯一作品数量通常不变，媒体大小减少；若发现原库记录错误，修正数量并说明原因。清理运行缓存不得清空作品索引、账号绑定或未完成任务。

## 10. 验收与性能验证

### 产品验收

1. 首页仅四个主要操作；未选目录不可下载，选中即展示库摘要。
2. 喜欢/收藏点击后直接执行；关注仅多一个作者选择步骤，没有预扫描确认页。
3. 首批可下载作品出现即可传输，后续列表仍可读取；不先拉完全部作者。
4. 关注目标 101、250、数千条均可连续处理，不在 100 条结束；作者列表也不被首批截断。
5. 一个作品来自多个来源，全库作品只算一条；不同路径副本大小如实累计，整理后空间降低。
6. 列表未读完不显示整体百分比；本次成功不含历史量；数字满足 C=S+E+F+X+P。
7. 队列空但生产者未结束不报完成；作者失败、分页异常、单条失败各有部分完成/阻塞状态。
8. 同一路径不被两个消费者同时写，图文与多段作品不以部分完成计成功。
9. 暂停/恢复、页面重载、写盘失败与跨文件版本不一致可恢复，不丢失败原因。
10. 整理中断、文件删除失败、记录保存失败均不会失去唯一有效副本或来源关系。
11. 运行下载时不执行全库哈希/目录核对/留存统计；必要媒体校验与进度保存仍执行。

### 性能验收方法

对比现有串行版本、流水线 1 路、流水线 2 路，在相同库规模、媒体类型和网络条件下记录：点击到首次媒体请求、首次媒体成功时间、整体吞吐、队列空闲比例、API 等待/主动节流、磁盘写入时间、UI 响应、CPU/内存峰值以及失败/限流比例。

启动不全盘扫描；下载内存不随媒体字节总量累积，队列有上限，媒体流式写入。大型索引按需加载/按键查询，避免多个 Worker 复制完整作品库。

并发提升必须以吞吐和失败率共同验证，不能承诺开两路就快两倍。若带宽、磁盘或接口已经成为瓶颈，保持较低并发。未测数据标未测，不把参数设计当基准结果。
